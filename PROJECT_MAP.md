# Project Map

Живой реестр того, что реализовано в проекте. Цель — чтобы понять "что уже есть и где" можно было по этому файлу, а не обходом всего кода.

**Правило:** создал компонент/сервис/interceptor/роут/включил опцию окружения — добавь строку сюда в том же коммите/PR, где это появилось. Не оставляй это только в коде.

## Структура / конвенции

- Скелет создан `ng new` (Angular 22, standalone, без `NgModule`); тест-раннер — встроенный Vitest-based `@angular/build:unit-test` (дефолт Angular 22, Karma/Jasmine сознательно не используются).
- Папки: `src/app/core/`, `src/app/shared/`, `src/app/features/`, `src/environments/` — назначение и путь-алиасы (`@core/*`, `@shared/*`, `@features/*`, `@env/*`) см. `README.md`.
- `src/environments/environment.ts` (dev) / `environment.prod.ts` — конфиги под алиас `@env/*`, `fileReplacements` в `angular.json` подставляет prod-версию при production-сборке.
- `ApiService` (`stream.Front#3`) проверен юнит-тестом на `HttpTestingController`, а не реальным вызовом к живому backend — на момент реализации у бэка не было ни `/health` (`streamer.API#7`), ни CORS (`streamer.API#5`). Реальная end-to-end проверка — когда обе появятся.
- ESLint (`@angular-eslint`) + Prettier настроены (`eslint.config.js`, `.prettierrc`, `.prettierignore`); `eslint-config-prettier` отключает конфликтующие с Prettier правила форматирования. Команды — см. `README.md`. Git-хуки сознательно не подключены.
- Конвенция loading/error/empty (`stream.Front#9`): loading — `Skeleton`, error — `ErrorMessage` (см. «Компоненты»). Empty-состояние **не** унифицировано намеренно — решается индивидуально по фиче.
- `initializeAuth` (`stream.Front#14`, `src/app/core/initializers/auth.initializer.ts`) — `provideAppInitializer` в `app.config.ts`: вызывает `AuthService.fetchCurrentUser()` до рендера маршрутов, любую ошибку (`401`/сеть) гасит, бутстрап не блокирует. Backend `/auth/me` (`streamer.API#16`) и CORS credentials-режим (`#19`) ещё не реализованы — проверено юнит-тестами на `HttpTestingController`, реальная e2e-проверка отложена (та же ситуация, что у `ApiService`/`AuthService`).

## Компоненты

- `NotificationList` — `src/app/shared/components/notification-list/` — toast-компонент, рендерит очередь `NotificationService.notifications`, крестик → `dismiss()`; подключён один раз в `app.html` (корневой layout). `z-index: 2100` — выше `ModalHost` (`2000`, `stream.Front#56`), по прямому запросу пользователя: тосты (в т.ч. auth-ошибки, `stream.Front#58`/`#59`) должны быть видны поверх открытой модалки, а не перекрываться её backdrop/тенью.
- `ModalHost` (`stream.Front#56`) — `src/app/shared/components/modal-host/` — единственный модальный слот приложения, подключён один раз в `app.html` рядом с `NotificationList` (корневой layout). Читает `ModalService.activeComponent()`/`activeData()`, при наличии активного компонента рендерит backdrop + панель, содержимое — через `NgComponentOutlet` (`[ngComponentOutletInputs]="{ data: ... }"`, содержимое-компонент получает данные через собственный `data = input<T>()`, отдельный DI-токен вроде `MODAL_DATA` не заведён). Закрытие — клик по backdrop (клик по самой панели не всплывает, `$event.stopPropagation()`), крестик — `public/icons/Close_btn.svg` (рисуется самим `ModalHost`, не дублируется в каждой модалке-потребителе; раньше был литеральный `&times;`, заменён на присланный пользователем SVG), `Esc` (`@HostListener('document:keydown.escape')`, срабатывает только когда есть активный компонент) — во всех случаях просто вызывает `ModalService.close()`; сама модалка-содержимое тоже может закрыть себя, инжектнув `ModalService` и вызвав `close()` напрямую. **Известные ограничения (сознательно вне скоупа `#56`):** без focus trap и без возврата фокуса на элемент-триггер после закрытия; без scroll-lock `body` при открытой модалке; без стека из нескольких одновременных модалок — `activeComponent` не массив, ровно один активный слот.
- `TextField` (`stream.Front#58`/`#59`) — `src/app/shared/components/text-field/` — основной текстовый инпут сайта (не только auth-формы), без `ReactiveFormsModule` (`[(value)]` через `model<string>('')` вместо `FormControl`, по прямому запросу пользователя). Inputs: `label`, `type` (`'text' | 'password'`, дефолт `'text'`), `required` (только визуальная звёздочка у лейбла, не блокирует сабмит), `placeholder`, `errorText` (инлайн-ошибка под полем + подсветка И бордера через `.text-field__control--invalid`, И лейбла через `.text-field__label--invalid` — по прямому запросу пользователя, раньше только бордер), `icon` (класс PrimeIcons, например `'pi pi-search'`). Иконка-префикс — опциональна, приоритет по прямому запросу пользователя: 1) `icon()` (PrimeIcons, `<i>`) → 2) спроецированный контент (`<ng-content select="[icon]">`, тот же приём, что у `DecorativeButton`) → 3) ничего — компартмент схлопывается через `.text-field__prefix-icon:empty { display: none }` (тот же приём, что `.button__icon:empty` у `DecorativeButton`). Раньше иконка выбиралась автоматически по `type()` (человечек/замок, inline SVG) и была обязательной — эти два SVG вынесены в статичные ассеты `public/icons/text-field-{person,lock}.svg` (цвет запечен в файле — `<img>` не наследует `currentColor`, в отличие от inline SVG), каждый вызывающий код теперь явно проецирует нужный (все 9 текущих usages обновлены, визуал не изменился). Компартмент иконки — 40×40 (высота контрола зафиксирована `height: 40px` явно — без этого компартмент растягивался под фактическую высоту инпута и получался прямоугольником, а не квадратом), `public/icons/User_input.svg` (референс от пользователя) — та же техника скруглённого левого угла + прямого правого края, что в `google_btn.svg`/`facebook_btn.svg`, цвет иконки — `$color-black` на `opacity: .5`. `type()="password"` — кнопка-глаз (inline SVG, без отдельного компартмента), переключает внутренний `isPasswordVisible` signal (не завязан на `type()` снаружи), `computed()` даёт реальный HTML-`type` инпута; `aria-label` кнопки меняется между «Показать пароль»/«Скрыть пароль». Каждый инстанс получает свой `uid` (тот же incremental-counter приём, что у `DecorativeButton`/`NavActiveIndicator`) — под связку `<label for>`/`id`. Цвета — светлая тема (`$color-e4e4e4` бордер контрола и разделителя иконки, `$color-ffffff` фон, `border-radius: 5px`), по `docs/figma/registration-structure.json` + `User_input.svg`. Шрифт (лейбл/инпут/ошибка) — Montserrat (по прямому запросу пользователя, раньше Nunito Sans из Figma text-стиля «Body»); размеры/интерлиньяж/трекинг из того же Figma-стиля не менялись (16/24, letter-spacing 3%). Лейбл — цвет `$color-black` (не литерал `$color-1e1e1e` напрямую — по прямому запросу пользователя). Story — `text-field.stories.ts` (Default/WithProjectedIcon/WithPrimeIcon/Password/Required/WithError). **Используется и в админ-панели** (по прямому запросу пользователя, светлая коробка намеренно оставлена как есть на тёмном фоне админки, не перетемизирована) — `AdminUsersPage` (поисковый фильтр, вместо сырого `pInputText`) и `AdminSchedulePage` (поля «Событие»/«Время» в drawer редактирования дня, вместо сырых `pInputText` с внешним `<label>`) — `InputTextModule` в обоих файлах больше не используется, удалён из `imports`.

Раньше использовался в `ScheduleWidget`/`DonatorsWidget` для loading-состояния списков — заменён там на встроенный скелетон-прелоадер `List` (`stream.Front#52`, по прямому запросу пользователя); сам компонент остаётся общей примитивом `stream.Front#9`-конвенции для не-`List` loading-UI, сейчас нигде не подключён

- `Button` (`stream.Front#89`) — `src/app/shared/components/button/` — тонкая обёртка над PrimeNG `pButton` для админ-панели (`AdminUsersPage`/`AdminSchedulePage`, `stream.Front#76`/`#77`, ранее использовавших сырую `pButton`-директиву напрямую без единого компонента). Не полный проксирующий враппер PrimeNG API — только пропсы, реально нужные текущим usages: `text` (`input.required<string>()`, содержимое кнопки), `severity` (тип `ButtonSeverity = 'danger'`, единственный нестандартный severity в usages — кнопки «Удалить»), `size` (тип `ButtonSize = 'small'`, единственный нестандартный размер в usages), `disabled`. Остальные PrimeNG severity/`outlined`/`text`-варианты и полная шкала размеров сознательно не заведены — отдельными задачами по мере необходимости (см. AC `#89`). `icon` — опциональный `input<string>()` (класс PrimeIcons, например `'pi pi-trash'`), рендерится как `<i [class]="iconClass">` перед текстом внутри самого `pButton`-хоста через `@if` — если не передан, `<i>` в DOM вообще не появляется (не пустой слот); выбран этот подход, а не content projection (как у `DecorativeButton`), потому что `pButton`-директива в PrimeNG 22 больше не имеет отдельного `icon`-инпута/дочерней `pButtonIcon`-директивы (deprecated с v21) — рекомендованный способ произвольного элемента внутри хоста ближе к простому input-строке для этого тонкого враппера, чем к кастомному SVG-слоту. `severity="danger"` перекрашен в `button.scss` через CSS-переменные, которые генерирует PrimeNG dt()-токенами (`--p-button-danger-background`/`-hover-background`/`-active-background`/`-border-color` и т.д.) — на значения уже существующего в проекте красного (`$color-cf1717`/`$color-c61718`, тот же, что у `ErrorMessage`), а не дефолтного Aura-красного из `AdminPreset` (тот его не переопределяет, см. «PrimeNG» ниже) — так же, как и остальные цвета проекта, не хардкожены инлайн, донастраиваются в одном месте без изменения структуры компонента. **`primeicons` package (`stream.Front#89`)** — до этой задачи не был установлен вовсе, из-за чего `icon()` изначально рендерил класс без реальных иконок (пустой квадрат/ничего): добавлен в зависимости (`npm install primeicons`) и подключён глобально в `angular.json` (`architect.build.options.styles`, `primeicons/primeicons.css` перед `src/styles.scss`) — без этого шага PrimeIcons-классы (`pi pi-*`) не резолвятся ни в одном компоненте проекта, не только в `Button`. **`severity="primary"` (дефолт, доуточнение по прямому запросу пользователя)** — тем же приёмом, что и `danger`, перекрашен в `button.scss` через `--p-button-primary-background`/`-border-color`/`-color` на `$color-f4d2a4`/`$color-f8ecb3`/`$color-76511c` (новые токены в `_variables.scss`, не из designTokens JSON-экспорта) — без этого рисовался бы цвет `AdminPreset`-палитры (`primary: palette('#e6c319')`). Hover/active-варианты не запрашивались и не переопределены — остаются производными от палитры `AdminPreset`. **Шрифт текста — Montserrat** (по прямому запросу пользователя) — обычный `button { font-family: vars.$font-family-montserrat }` в `button.scss` (`<button>` — прямой элемент шаблона этого компонента, не дочернего, обычной view-encapsulation достаточно, `::ng-deep` не понадобился); без этого рисовался бы дефолтный Aura-шрифт — `AdminPreset` шрифт не переопределяет, только цветовую палитру. **Расширение для публичного сайта (`stream.Front#95`)** — `text` стал необязательным (`input<string>()`) — icon-only режим для иконок-кнопок карточек турниров/новостей (сброс/глаз/сердце/воронка-фильтр); `[iconOnly]="!text()"` пробрасывается в `pButton` явно, а не через автоопределение директивы (то смотрит только на content-директивы `pButtonIcon`/`pButtonLabel`, которых этот компонент не использует). Новый `severity="contrast"` (тип `ButtonSeverity` расширен до `'danger' | 'contrast'`) — светлый фон/тёмная иконка, тем же приёмом CSS-переменных (`--p-button-contrast-background`/`-hover-background`/`-active-background`/`-border-color`/`-color`) на `$color-f9f9f9`/`$color-d9d9d9`/`$color-bfbfbf`/`$color-333333` — ориентир, `filter`-блок в `docs/figma/tournament1.json` (bg `rgb(249, 249, 249)`). Новый `active` input (`boolean`, дефолт `false`) — только визуальное "нажатое"/подсвеченное состояние (класс `button--active` в `button.scss`, переиспользует те же `--p-button-{severity}-active-*` токены, что PrimeNG уже применяет на реальный `:active`, просто делает их постоянными) — компонент не хранит и не вычисляет тоггл-состояние сам, значение приходит от вызывающего кода.
- `Badge` (`stream.Front#96`, доработан `stream.Front#107`) — `src/app/shared/components/badge/` — тонкая обёртка над PrimeNG `p-tag`. Inputs: `text` (`input.required<string>()` — в отличие от `Button`, подпись у бейджа не опциональна, icon-only режим не заводился), `severity` (`BadgeSeverity = ButtonSeverity | 'primary'` — та же палитра, что у `Button`, дефолт `'primary'`, по прямому запросу пользователя "цвета аналогично как у кнопки"; было `'admin' | 'moderator' | 'user'` — семантические имена ролей заменены на цветовую палитру, `AdminUsersPage.badgeSeverity()` теперь маппит роль напрямую на severity: `ADMIN→'danger'`, `MODERATOR→'info'`, `USER→'contrast'`), `color`/`textColor` (произвольные CSS-цвета фона/текста, независимо друг от друга перебивают `severity` — по прямому запросу пользователя). `tagSeverity()` — `'primary'` даёт `undefined` (без doп. severity-класса на `p-tag`, тот же приём, что у `Button` — дефолт без атрибута), остальные имена 1:1 совпадают с нативными `TagSeverity` PrimeNG (`primeng/types/tag`), в отличие от старой версии lookup-маппинг больше не нужен. Цвета — та же палитра, что у `Button` (`button.scss:34-119`, только фон/текст — `p-tag` не интерактивен, hover/active не нужны), CSS-переменные `--p-tag-{severity}-background`/`-color` на `:host` (`badge.scss`). `color()`/`textColor()` — прямой `[style.background]`/`[style.color]`-биндинг на `<p-tag>` (`badge.html`): `<p-tag>` — "host-class" компонент (класс `p-tag` навешен на собственный host-элемент, не вложенный див, см. `primeng-tag.mjs`), инлайн-стиль перебивает любой class-based override без `::ng-deep`/`!important`. Паддинг — `4px 8px` (`--p-tag-padding`, по значениям, присланным пользователем напрямую — оригинального Figma-экспорта для бейджа «Турнир» в `docs/figma/*.json` нет). Шрифт — Montserrat (по прямому запросу пользователя): у `p-tag` нет dt()-токена под font-family, задан обычным CSS-свойством на селекторе `p-tag` (не `::ng-deep` — этот тег написан прямо в шаблоне `badge.html`, несёт scope-атрибут этого компонента). Демо в Storybook — `badge.stories.ts` (`Shared/Badge`): все 6 severity рядом + свои цвета (проверено визуально через Playwright — рендер «ТУРНИР» с `color`/`textColor` практически 1:1 совпал с присланным пользователем референсом).
- `Select` (`stream.Front#94`) — `src/app/shared/components/select/` — тонкая обёртка над PrimeNG `p-select` для админ-панели (`AdminUsersPage`: фильтр по роли + селект роли в drawer «Изменить роль», ранее — сырой `p-select` напрямую). Причина, по которой напрямую нельзя — реальный баг PrimeNG, всплывший ТОЛЬКО в комбинации с `minDate` (см. подробный разбор ниже, у `DatepickerRange`): `isSelectable()` в `primeng-datepicker.mjs` читает `this.currentView()` только в ветке `minDate` (не `maxDate` — асимметрия в исходнике), что делает внутренний `effect()` для `minDate`/`maxDate` случайно зависимым от переключения date/month/year view; будясь при открытии month-picker, он в ту же волну будит СОСЕДНИЙ `effect()` для `defaultDate`, который безусловно перезаписывает текущий месяц обратно на `defaultDate`, откатывая ЛЮБУЮ навигацию пользователя. **`minDate`/`maxDate`** — нативные пропы `p-datepicker` (даты вне диапазона рендерятся `disabled`, физически некликабельны), пробрасываются как есть — понадобились `DatepickerRange`, чтобы жёстко запретить выбрать в одном календаре дату по не ту сторону от даты в другом (по прямому запросу пользователя). **`rangeHighlight`** (`[Date, Date] | null`, по прямому запросу пользователя — визуально выделить весь выбранный диапазон, не только его края) — реализовано через `dateTemplate` (`<ng-template #date>` в `datepicker.html`, единственный официальный способ PrimeNG добавить что-то на каждую ячейку дня — `::ng-deep` на `.p-datepicker-day` не умеет отличить одну дату от другой, CSS не считает даты) — рисует `<span class="day-range-fill">` позади номера дня, залитый (`$color-e1bf90`, тот же оттенок, что у hover/промежуточных дней `range`-режима выше), если дата строго МЕЖДУ `start`/`end` (сами края красятся штатной `.p-datepicker-day-selected` для `value` конкретного инстанса, см. выше). Убрали `z-index` вовсе (расчёт на то, что порядок в разметке — заливка раньше `{{ date.day }}` — сам расставит слои), но это ОКАЗАЛОСЬ НЕВЕРНО тоже: по CSS 2.1 Appendix E позиционированные потомки без `z-index` (т.е. `auto`) красятся стекинг-контекстом ПОЗЖЕ обычного строчного контента НЕЗАВИСИМО от порядка в DOM — залитые (промежуточные) дни диапазона полностью теряли цифру, видимую только у самих концов диапазона (`.p-datepicker-day-selected`, где заливка прозрачна — `isDateInRange()` намеренно исключает края строгим `>`/`<`). - `DatepickerRange` (`stream.Front#109`) — `src/app/shared/components/datepicker-range/` — композиция из ДВУХ независимых `Datepicker(inline, selectionMode="single")` для произвольной разницы между показанными месяцами (например, слева январь — справа декабрь), которую `numberOfMonths` у `Datepicker` не даёт (см. выше). **Почему НЕ `selectionMode="range"` с общим `value` между двумя инстансами** (первая попытка, не сработала — важный урок, см. подробный комментарий в `datepicker-range.ts`): у `p-datepicker` ЛЮБАЯ внешняя перезапись `value` (в т.ч. тем же значением, которое инстанс только что сам эмитировал через `(ngModelChange)` — а именно так ведёт себя `[ngModel]="value()"` на `Datepicker`, сигнал перегоняет то же значение вниз при каждом ре-рендере) вызывает `writeControlValue()` → `updateUI()`, которая безусловно пересчитывает показанный месяц из `value` (`primeng-datepicker.mjs`). Для незавершённой пары `[date, null]` там баг: код берёт `propValue[1]` (конец диапазона), тот `null` → `isValidDate(null)` ложь → фолбэк на `new Date()` — оба календаря прыгали на "сегодня" уже на первом клике вместо января/декабря; даже без этого бага для ЗАВЕРШЁННОЙ пары `updateUI()` навигировал бы ОБА календаря на месяц `value[1]`, разрушая саму идею "разные фиксированные месяцы". Итоговое решение — `selectionMode="single"` на каждом инстансе (там нет партиал-состояния: клик всегда даёт полную дату из уже показанного месяца, "прыжок" на её же месяц — no-op, ничего не ломается), каждый со своим ЛОКАЛЬНЫМ `[(value)]` (`leftValue`/`rightValue`, `model()` на `DatepickerRange`), никогда не связанным с другим инстансом напрямую. **Левее не может быть правее** (по прямому запросу пользователя) — `[maxDate]` левого календаря = `rightDate()`, `[minDate]` правого = `leftDate()` (нативные `Datepicker`-пропы, см. выше): недопустимые даты — `disabled`, физически некликабельны, не пост-фактум сортировка значения; из-за этого `value` больше не нужно сортировать — порядок `left <= right` гарантирован самим UI. **Заливка выбранного диапазона** (по прямому запросу пользователя) — `[rangeHighlight]="value()"` прокинут в оба календаря (см. `rangeHighlight` у `Datepicker` выше); работает и для дней, до которых долистали вручную в любом из двух календарей — сравнение чисто по датам, не привязано к тому, какой инстанс их показывает. **Единая карточка** (по прямому запросу пользователя — "как единый элемент") — общие рамка/тень/скругление на `:host` этого компонента, у дочерних панелей (`:host ::ng-deep .app-datepicker-panel`, реальный физический предок в DOM — в inline-режиме панель НЕ уносится `appendTo`, см. `Datepicker`) рамка/тень сняты, `border-radius: 0`; вместо расчёта скругления только для "внешних" углов каждой панели по отдельности (как у `ButtonGroup`) — более простой приём: панели становятся прямоугольными, а `overflow: hidden` на этой обёртке сам обрезает их по скруглению внешней рамки; между календарями — `border-right` на первом (не отдельная разделительная `<div>`). `value` — **только для чтения** (`computed()`, не `model()` — задать его снаружи означало бы переписать `value` одного/обоих `p-datepicker`, вернув ровно ту же проблему), пара `[leftDate, rightDate]`. `leftDefaultDate`/`rightDefaultDate` — какой месяц показан в каждом календаре изначально, пробрасываются в `defaultDate` соответствующего `Datepicker`; дальше каждый календарь листается своими стрелками независимо. **Баг PrimeNG: навигация по месяцам ломалась ТОЛЬКО у календаря с `minDate`** (обнаружен уже после выбора полного периода — правый календарь переставал реагировать на выбор другого месяца, откатываясь обратно; левый работал исправно) — см. подробный разбор в `datepicker.ts` у `defaultDate`/`resolvedDefaultDate`: причина в `isSelectable()` (`primeng-datepicker.mjs`), которая читает `this.currentView()` ТОЛЬКО в ветке проверки `minDate` (у `maxDate` аналогичного чтения нет — асимметрия в исходнике PrimeNG); это создаёт СЛУЧАЙНУЮ зависимость внутреннего `effect()` для `minDate`/`maxDate` от переключения date/month/year view, из-за которой открытие month-picker будит и СОСЕДНИЙ `effect()` для `defaultDate` — тот безусловно перезаписывает `currentMonth`/`currentYear` обратно на `defaultDate`. Исправлено на нашей стороне (`Datepicker`, не в `DatepickerRange`) — `defaultDate` нужен только для НАЧАЛЬНОГО месяца, поэтому пробрасывается в `p-datepicker` не напрямую, а через `resolvedDefaultDate` (`computed`, "гасится" в `undefined` через `queueMicrotask` в `ngOnInit()` сразу после первого применения) — эффект PrimeNG проверяет `defaultDate !== undefined` и с этого момента, даже спонтанно перезапустившись, ничего не перезаписывает. Юнит-тесты (`datepicker-range.spec.ts`) покрывают рендер двух `app-datepicker`, разные стартовые месяцы, то, что клик по дате НЕ сдвигает месяц ни в одном из календарей, корректный упорядоченный диапазон при клике в любом порядке, `disabled`-состояние дат по не ту сторону от уже выбранной (`maxDate`/`minDate`), заливку дней строго между выбранными (`rangeHighlight`, в пределах одного видимого месяца) и регрессию на баг с навигацией по месяцам у календаря с `minDate` ПОСЛЕ выбора периода (месяцы в тесте — на английском: `ru-translation.ts` подключена глобально только в `app.config.ts`/`.storybook/preview.ts`, `TestBed` её не использует). Растяжение — `anchoredScale(anchor, scale)` (та же формула, что у `DecorativeButton`), анкор — собственная вершина контура каждой фигуры (подложка — `x=15`, граница — `x=14.75`); `scale` — `(исходная ширина + firstSegmentShiftPx()) / исходная ширина`. Острия/«крючки» — фиксированного размера, только сдвигаются вместе (`borderCurlTransform()` = `translate(firstSegmentShiftPx() 0)`). `filter2_d`/`filter5_d` регионы — статично расширены (тот же приём, что у `DecorativeButton`/`SectionTitle`: маленький исходный регион обрезал бы декор при растяжении, Chromium не пересчитывает регион фильтра реактивно). Демо на `/kit` — 4-я строка с первым сегментом `width: '100px'` (вместо базовых `48px`).
  **Зеркально — декор в правой части строки привязан к фактическому боксу ПОСЛЕДНЕГО сегмента** (подложка — `paint5_radial`-path, простой прямоугольник, весь целиком растягивается; граница — `filter4_d`/`paint7_linear`). `lastSegmentShiftPx()` — `segmentBoxes()[последний].width − LAST_SEGMENT_BASELINE_WIDTH_PX(56)`, той же природы, что `firstSegmentShiftPx()` (тоже работает для "резиновой" ширины). Анкор растяжения — **фиксированный правый край** (`x=643.75`, край самой пилюли) у обеих фигур, растягиваются влево, зеркально левой стороне. «Крючок» границы сдвигается **влево** (`rightBorderHookTransform()` = `translate(-lastSegmentShiftPx() 0)`). `filter1_d`/`filter4_d` регионы аналогично статично расширены. Демо на `/kit` — 5-я строка с последним сегментом `width: '100px'` (вместо базовых `56px`); 6-я строка — регрессионный демо-кейс на "резиновый" последний сегмент («Кастомная игра», `width: 1`), теперь получает полноразмерный (не узкий, как раньше) бокс подложки и текста.

Без значения на конкретном индексе — `'left'`. **Позиция каждого разделителя (включая крайние) — ОДНА общая формула**: середина зазора между боксом сегмента `i` и `i+1` (`segmentBoxes()[i].x + segmentBoxes()[i].width + BOUNDARY_GAP/2`) — раньше крайние разделители были особым случаем (жёстко привязаны к исходному узору Schedule.svg отдельной формулой, чтобы сохранить нужный зазор от подложки), но раз теперь подложка САМА выведена из той же `segmentBoxes()`, разделитель автоматически остаётся на нужном расстоянии от неё без специального случая. Сама графика узора не меняется — `leftOrnamentTransform(x)`/`rightOrnamentTransform(x)` просто переносят её (`translate(targetX - ownCenterX, 0)`, `ownCenterX` — фиксированный центр узора в исходных Schedule.svg-координатах) в вычисленную точку, не растягивают — чисто декоративный перенос. Рендерится через `@for` по `dividerInstances()` с `@if`/`@else if` на тип, `id` маски — `uid` + индекс инстанса (может быть несколько разделителей одного типа на строку). `List`/`ListItemData` прокидывают это же поле (`dividers?: ListItemDividers`), дефолт `[]` в шаблоне (`item.dividers ?? Единственная тонкость — сам текст: простой зеркал контейнера отразил бы и глифы (нечитаемо), поэтому `.day-row__content` зеркалится ЕЩЁ РАЗ (`.day-row--mirrored .day-row__content { transform: scaleX(-1) }`) — стандартный приём "зеркалим родителя, отзеркаливаем обратно нужного ребёнка" (используется для разворота иконок под RTL): текст остаётся читаемым, а его позиция (унаследованная от уже отражённого родителя) остаётся зеркальной. `List`/`ListItemData` прокидывают то же поле (`direction?: ListItemDirection`), дефолт `'left'` в шаблоне. Демо на `/kit` — 8-я строка, `direction: 'right'`.
  **Баг, найденный на `DonatorsWidget` (`stream.Front#31`) и исправленный в компоненте:** `scaleX(-1)` зеркалит декор (подложки/разделители/центральные подложки) ОДНОКРАТНО, а `.day-row__content` (текст) — ДВАЖДЫ, т.е. видимая позиция ТЕКСТА при `direction: 'right'` не меняется вовсе (остаётся как при `'left'`), а ДЕКОР физически переезжает на другую сторону экрана. Подложка-«стрелка»/её граница при этом были рассчитаны на растяжение под ширину бокса сегмента по ФИКСИРОВАННОМУ индексу (`segmentBoxes()[0]` для начальной, `[length-1]` для конечной) — при `direction: 'right'` она экранно уезжает под сегмент с ПРОТИВОПОЛОЖНЫМ индексом, но продолжала растягиваться под ширину "своего" (неверного) сегмента. При близких по ширине сегментах (Schedule: 48px/56px) расхождение малозаметно, при сильно разных (Donators: резиновый ник + `90px` сумма) — подложка становится гигантской и налезает не на тот сегмент. **Исправлено**: `startBoxIndex()`/`endBoxIndex()` (`list-item.ts`) — при `direction: 'right'` возвращают ПРОТИВОПОЛОЖНЫЙ индекс (тот, что реально окажется под подложкой на экране после зеркалирования), `firstSegmentShiftPx()`/`lastSegmentShiftPx()` считают сдвиг от него, не от фиксированного `[0]`/`[length-1]`. `dividerInstances()`/`centerSubplates()` — та же логика: их `x` при `direction: 'right'` зеркально пересчитывается (`ROW_WIDTH_PX - x`, `ROW_WIDTH_PX = 644` — ширина `.day-row`, ось зеркалирования CSS `scaleX(-1)`), чтобы декоративный разделитель/центральная подложка визуально остались на границе ТЕКСТОВЫХ (не зеркалящихся) боксов, а не уехали в произвольную точку. Регрессия закрыта тестами в `list-item.spec.ts` (асимметричные сегменты + `direction: 'right'` — подложки растягиваются под верный бокс, разделитель — на границе текстовых боксов).
  **Роль сегмента определяет тип его подложки — начальная/конечная/центральная**, по прямому запросу пользователя ("если элементов 2 — только начальная и конечная, если 4 — есть начальная, конечная и 2 центральные, если 1 — только центральная"): 1-й сегмент (при `segments().length >= 2`, `hasStartAndEnd()` в `list-item.ts`) — «начальная», последний (при >=2) — «конечная», сегменты МЕЖДУ ними (индексы `1..N-2`) — «центральная», по одной штуке на каждый (`centerSubplates()`, N-2 штук: 0 при N<=2, 1 при N=3, 2 при N=4). При N=1 начальной/конечной нет вовсе (нет `@if (hasStartAndEnd())`-блоков в шаблоне — сама пилюля-силуэт `filter0_d`/`filter3_d` рендерится как обычно, это её собственная форма, не подложка) — только 1 центральная подложка со статичной геометрией (соло-бокс, см. выше).
  Каждая центральная подложка (`paint6_radial`-rect, `<rect>` без 9-slice/`clip-path`, простой прямоугольник) — **ровно `segmentBoxes()` её собственного сегмента**, `centerSubplates() = segmentBoxes().slice(1, -1)` — та же геометрия, что и у текста, никакой отдельной формулы «отступ от разделителя» не нужно (уже заложено в `BOUNDARY_GAP` при построении самих боксов). Каждая — свой инстанс градиента `paint6_radial-{uid}-{index}` (общий на все не подходит: у каждой свои `x`/`width`, `gradientTransform` пересчитывается индивидуально через `centerSubplateGradientTransform()`, формула центр/масштаб).

Семантика этих иконок в экспорте не зафиксирована — реализована как **сортировка архива** по просмотрам/лайкам (два взаимоисключающих тоггла) + сброс; требует подтверждения, когда Figma снова будет доступна. `filterChange` сайдбара применяется и к сетке, и к архиву (сайдбар стоит в тулбаре архива, но фильтрует раздел целиком); фильтр по периоду сравнивает по границам дня. - `GoogleAuthService` (`stream.Front#15`, `renderButton()` — `stream.Front#72`, `connectButton()` — `stream.Front#82`) — `src/app/core/services/` — грузит Google Identity Services JS SDK (`https://accounts.google.com/gsi/client`) динамическим `<script>`-тегом (не инлайновый скрипт в `index.html`), кэширует промис загрузки. **`prompt()`/One Tap флоу (изначальная реализация) заменён на `renderButton()`** — `prompt()` требует FedCM API и падает с 403 на внутреннем `/gsi/status`-статус-чеке везде, где заблокированы сторонние cookie (Firefox и другие браузеры вне Chromium; `use_fedcm_for_prompt: true` чинит это только в Chromium — обнаружено при ручном тестировании `stream.Front#72`) — это архитектурное ограничение самого API, не баг конфигурации. `renderButton(container: HTMLElement): Observable<CurrentUser>` рендерит официальную Google-кнопку (iframe с доменом `accounts.google.com`, поэтому клик — прямое взаимодействие с доменом Google, а не сторонний контекст) внутрь переданного элемента; `initialize()` вызывается один раз (idempotent, `initialized` флаг) с колбэком, кладущим ID-токен во внутренний `Subject<string>` (не резолвит Observable напрямую — `initialize()`/колбэк глобальны, `renderButton()` может дергаться из разных модалок), каждый вызов возвращает `credentialSubject.pipe(take(1), switchMap(loginWithGoogle))` — одна подписка получает ровно один результат, не подхватывая чужие эмиты. Если пользователь закрыл попап без входа — колбэк не вызывается, Observable просто не эмитит (не ошибка, GIS не даёт сигнала отмены для `renderButton()`). Проверено юнит-тестами с замоканным `window.google` и `loadScript()`.

## Interceptors / Guards

- `withCredentialsInterceptor` (`stream.Front#14`) — `src/app/core/interceptors/` — форсит `withCredentials: true` на всех HTTP-запросах приложения (не только через `AuthService`/`ApiService`), чтобы httpOnly auth-cookie уходила глобально; подключён в `app.config.ts` через `provideHttpClient(withInterceptors([...]))`
- `authInterceptor` (`stream.Front#5`) — `src/app/core/interceptors/` — на `401` вызывает `AuthService.logout()` и показывает уведомление через `NotificationService` (без редиректа — окно логина/регистрации реализовано как модалка, без отдельного роута). Исключение — запросы к `/auth/*`: `401` от `/auth/me` (гость, см. `#14`) и `/auth/login`/`/auth/google` (неверные креды) не триггерят logout, а `/auth/logout` явно исключён из собственной же логики, иначе получился бы бесконечный цикл. Ошибка не глотается — пробрасывается дальше вызывающему коду. Backend-эндпоинты и CORS credentials-режим (`streamer.API#16-19`) ещё не реализованы — проверено юнит-тестами на `HttpTestingController`.
- `authGuard` (`stream.Front#20`) — `src/app/core/guards/` — `CanActivateFn`, проверяет только факт авторизации (`AuthService.isAuthenticated()`), без ролей (RBAC — отдельная задача). Неавторизованных редиректит на `/` (не на `/login` — окно логина модалка, без роута). Ложный редирект до завершения `fetchCurrentUser()` при старте исключён архитектурно — `provideAppInitializer` (`#14`) блокирует первую навигацию роутера до готовности `currentUser`, поэтому сам guard не нуждается в асинхронном ожидании. Первое реальное применение — `/account`.
- `adminGuard` (`stream.Front#74`) — `src/app/core/guards/` — `CanActivateFn`, RBAC-проверка роли `ADMIN` (`authService.currentUser()?.role === 'ADMIN'`). Не дублирует проверку факта авторизации — используется на роуте вместе с `authGuard` (`canActivate: [authGuard, adminGuard]`, именно в этом порядке), сам полагается на то, что `currentUser` уже определён к моменту своей работы. Редирект не-ADMIN — на `/`, тот же паттерн, что у `authGuard`.

- `src/styles/_mixins.scss` (`stream.Front#37`) — миксины, названные по буквальному имени Figma text-стиля (не выдуманная роль), та же конвенция именования, что у `_variables.scss`. Подключается через `@use 'mixins';`, применяется как `@include mixins.<имя>;`. Два:
  - `h1` (Montserrat Bold 28/36, letter-spacing 8%) — Figma text-стиль «H1», первый компонент с именованным многосвойственным text-стилем (раньше, у `DecorativeButton`, типографика собиралась россыпью токенов инлайн в самом компоненте — там это осталось, миксин не ретроактивен); также используется в `AuthModalShell.__title` (`stream.Front#58`/`#59`).
  - `mainNav` (`stream.Front#48`) — Figma text-стиль «Main Nav» (Montserrat Medium 16/24, letter-spacing 8%) + `text-transform: uppercase` (по прямому запросу пользователя — капс через CSS, не хардкод в лейблах `navItems`); применяется на `.shell__nav-link`. `AuthModalShell.__footer-text` (`stream.Front#58`/`#59`) использует те же токены типографики inline (НЕ этот миксин — там нужен обычный регистр текста, не капс).
- `src/index.html` — подключение `Montserrat`/`Nunito Sans` через Google Fonts (`<link>`, веса 400/500/600/700 для обеих семей) — до этого `$font-family-montserrat`/`$font-family-nunito-sans` были только именами в CSS без реального шрифта, браузер молча откатывался на системный sans-serif (баг проявлялся визуально на auth-модалках, `stream.Front#58`/`#59`, но касался и `DecorativeButton`/`Shell`/всех остальных мест, использующих эти переменные).
- `src/styles/_reset.scss` — global reset (box-sizing, обнуление margin/list/link-стилей), применяется один раз через `src/styles.scss`. Плюс (`stream.Front#49`, по прямому запросу пользователя) базовый фон сайта на `html` — тот же радиальный градиент, что у `MainCarousel` (`$color-1e00b2` → `$color-0d004d`), и `color: $color-ffffff` на `body` — чтобы страницы без собственного полноэкранного фона (заглушки Новости/Турниры и любые будущие) не оставались белыми под прозрачным `Shell`.

## PrimeNG (`stream.Front#75`)

- `primeng@22`/`@primeuix/themes@3` — подключены в `app.config.ts` через `providePrimeNG()`, **глобально**, но PrimeNG-компоненты в проекте реально используются только внутри админ-панели (`stream.Front#76`/`#77` и далее) — остальной (не-админский) сайт продолжает жить на собственных компонентах (`DecorativeButton`, `SectionTitle` и т.д.), их PrimeNG нигде не заменяет
- `AdminPreset` (`src/app/core/primeng/admin-preset.ts`) — `definePreset(Aura, {...})` поверх дефолтного пресета `Aura`: border-radius/spacing/типографика — дефолтные значения `Aura` (не переопределяются), перекрашена ТОЛЬКО цветовая палитра через `palette()` (`@primeuix/themes`) из реальных цветов проекта — `primary` из `$color-e6c319` (золотой акцент, как у кнопки «Поддержать»/`NavActiveIndicator`), `surface` косвенно — переопределены primitive-шкалы `slate`/`zinc` (на которые semantic.surface ссылается через `light-dark(...)`) из `$color-1e1e1e` (`$color-black`)
- **Форс тёмного варианта** — `providePrimeNG({ theme: { options: { darkModeSelector: '.p-dark' } } })` + класс `p-dark` на `<html>` (`src/index.html`, статично, без переключателя); дефолт PrimeNG (`darkModeSelector: 'system'`) следует `prefers-color-scheme` ОС посетителя, что не подходит фиксированному тёмному визуалу сайта — без форса компоненты в браузере со светлой системной темой рендерились бы светлыми (белый фон таблицы и т.п., проверено вручную, несоответствие всплыло только в реальном браузере, не в юнит-тестах)
- **Лицензия** — PrimeNG 22 перешла на коммерческую модель (`PrimeUI License`, `node_modules/primeng/LICENSE.md`): бесплатна по Community-условиям (revenue/команда ниже порогов), но требует валидный license key, иначе сама библиотека показывает фиксированный баннер «Invalid PrimeUI License» **поверх любой страницы сайта**, не только там, где используются PrimeNG-компоненты — встроенное поведение самого `providePrimeNG()` при инициализации, не то, что можно ограничить только админкой программно. Key передаётся `providePrimeNG({ license: environment.primengLicenseKey })`; `environment.primengLicenseKey` — плейсхолдер (пусто) до того, как пользователь впишет реальный Community-ключ (см. «Опции окружения» ниже)
- Демо-компонент — `p-table` под `AdminPreset`, story `PrimeNG/AdminPreset` в Storybook (`stream.Front#98`, см. «UI-kit / Storybook» ниже) — только проверка темы/интеграции, не реальное использование
