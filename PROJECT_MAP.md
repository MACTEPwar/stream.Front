# Project Map

Живой реестр того, что реализовано в проекте. Цель — чтобы понять "что уже есть и где" можно было по этому файлу, а не обходом всего кода.

**Правило:** создал компонент/сервис/interceptor/роут/включил опцию окружения — добавь строку сюда в том же коммите/PR, где это появилось. Не оставляй это только в коде.

## Структура / конвенции

- Скелет создан `ng new` (Angular 22, standalone, без `NgModule`); тест-раннер — встроенный Vitest-based `@angular/build:unit-test` (дефолт Angular 22, Karma/Jasmine сознательно не используются).
- Папки: `src/app/core/`, `src/app/shared/`, `src/app/features/`, `src/environments/` — назначение и путь-алиасы (`@core/*`, `@shared/*`, `@features/*`, `@env/*`) см. `README.md`.
- `src/environments/environment.ts` (dev) / `environment.prod.ts` — конфиги под алиас `@env/*`, `fileReplacements` в `angular.json` подставляет prod-версию при production-сборке.
- `ApiService` (`stream.Front#3`) проверен юнит-тестом на `HttpTestingController`, а не реальным вызовом к живому backend — на момент реализации у бэка не было ни `/health` (`streamer.API#7`), ни CORS (`streamer.API#5`). Реальная end-to-end проверка — когда обе появятся.
- ESLint (`@angular-eslint`) + Prettier настроены (`eslint.config.js`, `.prettierrc`, `.prettierignore`); `eslint-config-prettier` отключает конфликтующие с Prettier правила форматирования. Команды — см. `README.md`. Git-хуки сознательно не подключены.
- Конвенция loading/error/empty (`stream.Front#9`): loading — `Skeleton`, error — `ErrorMessage` (см. «Компоненты»). Empty-состояние **не** унифицировано намеренно — решается индивидуально по фиче.
- `initializeAuth` (`stream.Front#14`, `src/app/core/initializers/auth.initializer.ts`) — `provideAppInitializer` в `app.config.ts`: вызывает `AuthService.fetchCurrentUser()` до рендера маршрутов, любую ошибку (`401`/сеть) гасит, бутстрап не блокирует. Backend `/auth/me` (`streamer.API#16`) и CORS credentials-режим (`#19`) ещё не реализованы — проверено юнит-тестами на `HttpTestingController`, реальная e2e-проверка отложена (та же ситуация, что у `ApiService`/`AuthService`).
- **`@angular/cdk` (`stream.Front#122`)** — первый заход Angular CDK в проект, версия `^22.1.0` (совместимая мажорная с `@angular/core@^22.0.0`). Первый (и пока единственный) используемый модуль — `@angular/cdk/layout` (`BreakpointObserver`), адаптивная страница «Новости» (`NewsPage`) и `ModalHost` (мобильный bottom sheet). Аудит других мест проекта, где CDK мог бы заменить ручные реализации (`ResizeObserver`-приёмы у `SectionTitle`/`NavActiveIndicator`, голые Pointer Events у `PinnedGridEditor` и т.п.) — отдельная будущая задача (`stream.Front#124`), не в рамках `#122`.

## Компоненты

- `NotificationList` — `src/app/shared/components/notification-list/` — toast-компонент, рендерит очередь `NotificationService.notifications`, крестик → `dismiss()`; подключён один раз в `app.html` (корневой layout). `z-index: 2100` — выше `ModalHost` (`2000`, `stream.Front#56`), по прямому запросу пользователя: тосты (в т.ч. auth-ошибки, `stream.Front#58`/`#59`) должны быть видны поверх открытой модалки, а не перекрываться её backdrop/тенью.
- `ModalHost` (`stream.Front#56`) — `src/app/shared/components/modal-host/` — единственный модальный слот приложения, подключён один раз в `app.html` рядом с `NotificationList` (корневой layout). Читает `ModalService.activeComponent()`/`activeData()`, при наличии активного компонента рендерит backdrop + панель, содержимое — через `NgComponentOutlet` (`[ngComponentOutletInputs]="{ data: ... }"`, содержимое-компонент получает данные через собственный `data = input<T>()`, отдельный DI-токен вроде `MODAL_DATA` не заведён). Закрытие — клик по backdrop (клик по самой панели не всплывает, `$event.stopPropagation()`), крестик — `public/icons/Close_btn.svg` (рисуется самим `ModalHost`, не дублируется в каждой модалке-потребителе; раньше был литеральный `&times;`, заменён на присланный пользователем SVG), `Esc` (`@HostListener('document:keydown.escape')`, срабатывает только когда есть активный компонент) — во всех случаях просто вызывает `ModalService.close()`; сама модалка-содержимое тоже может закрыть себя, инжектнув `ModalService` и вызвав `close()` напрямую. **Известные ограничения (сознательно вне скоупа `#56`):** без focus trap и без возврата фокуса на элемент-триггер после закрытия; без scroll-lock `body` при открытой модалке; без стека из нескольких одновременных модалок — `activeComponent` не массив, ровно один активный слот.
  **Мобильный bottom sheet (`stream.Front#122`)** — `ModalService.open()` принимает третий необязательный параметр `presentation: 'default' | 'sheet-on-mobile'` (`ModalPresentation`, дефолт `'default'`, читается `ModalHost` через `activePresentation()`, сбрасывается в `'default'` при `close()`). `ModalHost` инжектит `BreakpointObserver` (`@angular/cdk/layout`, `SMALL_QUERY` из `@shared/utils/breakpoints`) и вычисляет `isSheetVariant` (`computed`): `true` только когда одновременно активная модалка попросила `'sheet-on-mobile'` И реальная ширина сейчас `small` (`< 768px`) — классы `.modal-host__backdrop--sheet`/`.modal-host__panel--sheet` (`modal-host.scss`: панель прижата к низу вьюпорта на всю ширину, скруглены только верхние углы) навешиваются условно через `[class.*]`. `ModalHost` остаётся общим слотом без знания о конкретных модалках-потребителях — решение "нужна ли ЭТОЙ модалке мобильная шторка" принимает вызывающий код через `ModalService.open()` (первый и пока единственный потребитель — `NewsDetailModal`, см. `NewsPage.onOpenDetail()`); раскладку/пропорции содержимого под узкую ширину донастраивает сам компонент-модалка (`@include bp.small` в его собственном SCSS), не `ModalHost`.
- `TextField` (`stream.Front#58`/`#59`) — `src/app/shared/components/text-field/` — основной текстовый инпут сайта (не только auth-формы), без `ReactiveFormsModule` (`[(value)]` через `model<string>('')` вместо `FormControl`, по прямому запросу пользователя). Inputs: `label`, `type` (`'text' | 'password'`, дефолт `'text'`), `required` (только визуальная звёздочка у лейбла, не блокирует сабмит), `placeholder`, `errorText` (инлайн-ошибка под полем + подсветка И бордера через `.text-field__control--invalid`, И лейбла через `.text-field__label--invalid` — по прямому запросу пользователя, раньше только бордер), `icon` (класс PrimeIcons, например `'pi pi-search'`). Иконка-префикс — опциональна, приоритет по прямому запросу пользователя: 1) `icon()` (PrimeIcons, `<i>`) → 2) спроецированный контент (`<ng-content select="[icon]">`, тот же приём, что у `DecorativeButton`) → 3) ничего — компартмент схлопывается через `.text-field__prefix-icon:empty { display: none }` (тот же приём, что `.button__icon:empty` у `DecorativeButton`). Раньше иконка выбиралась автоматически по `type()` (человечек/замок, inline SVG) и была обязательной — эти два SVG вынесены в статичные ассеты `public/icons/text-field-{person,lock}.svg` (цвет запечен в файле — `<img>` не наследует `currentColor`, в отличие от inline SVG), каждый вызывающий код теперь явно проецирует нужный (все 9 текущих usages обновлены, визуал не изменился). Компартмент иконки — 40×40 (высота контрола зафиксирована `height: 40px` явно — без этого компартмент растягивался под фактическую высоту инпута и получался прямоугольником, а не квадратом), `public/icons/User_input.svg` (референс от пользователя) — та же техника скруглённого левого угла + прямого правого края, что в `google_btn.svg`/`facebook_btn.svg`, цвет иконки — `$color-black` на `opacity: .5`. `type()="password"` — кнопка-глаз (inline SVG, без отдельного компартмента), переключает внутренний `isPasswordVisible` signal (не завязан на `type()` снаружи), `computed()` даёт реальный HTML-`type` инпута; `aria-label` кнопки меняется между «Показать пароль»/«Скрыть пароль». Каждый инстанс получает свой `uid` (тот же incremental-counter приём, что у `DecorativeButton`/`NavActiveIndicator`) — под связку `<label for>`/`id`. Цвета — светлая тема (`$color-e4e4e4` бордер контрола и разделителя иконки, `$color-ffffff` фон, `border-radius: 5px`), по `docs/figma/registration-structure.json` + `User_input.svg`. Шрифт (лейбл/инпут/ошибка) — Montserrat (по прямому запросу пользователя, раньше Nunito Sans из Figma text-стиля «Body»); размеры/интерлиньяж/трекинг из того же Figma-стиля не менялись (16/24, letter-spacing 3%). Лейбл — цвет `$color-black` (не литерал `$color-1e1e1e` напрямую — по прямому запросу пользователя). Story — `text-field.stories.ts` (Default/WithProjectedIcon/WithPrimeIcon/Password/Required/WithError). **Используется и в админ-панели** (по прямому запросу пользователя, светлая коробка намеренно оставлена как есть на тёмном фоне админки, не перетемизирована) — `AdminUsersPage` (поисковый фильтр, вместо сырого `pInputText`) и `AdminSchedulePage` (поля «Событие»/«Время» в drawer редактирования дня, вместо сырых `pInputText` с внешним `<label>`) — `InputTextModule` в обоих файлах больше не используется, удалён из `imports`.

Точные размеры — `docs/figma/registration-structure.json`: модалка 1140×640, фон правой панели `$color-f9f9f9`. Inputs: `title` (required), `footerText`, `footerLinkText`; output `footerLinkClick`. - `Skeleton` — `src/app/shared/components/skeleton/` — loading-плейсхолдер с shimmer-анимацией, форма/размер под конкретный элемент через inputs `width`/`height`/`radius` (дефолты `100%`/`16px`/`4px`). Раньше использовался в `ScheduleWidget`/`DonatorsWidget` для loading-состояния списков — заменён там на встроенный скелетон-прелоадер `List` (`stream.Front#52`, по прямому запросу пользователя); сам компонент остаётся общей примитивом `stream.Front#9`-конвенции для не-`List` loading-UI, сейчас нигде не подключён
- `ErrorMessage` — `src/app/shared/components/error-message/` — единый текст ошибки уровня элемента, дефолт «Ошибка загрузки» (`message` input для редких переопределений)
- `FocalPointPicker` (`pinned-grid-rework`) — `src/app/shared/components/focal-point-picker/` — переиспользуемый пикер точки фокуса картинки, по прямому запросу пользователя «где выбирается та самая точка, я не вижу» (заменяет убранные `imageScale`/`imageOffsetX`/`imageOffsetY` у `PinnedNewsCardStyle`). Inputs: `imageUrl` (`input.required<string>()`), `point` (`FocalPointValue | null`, `null` = центр 50/50); outputs `pointChange`/`pointCommit`. Показывает картинку целиком, клик/перетаскивание маркера — голые Pointer Events (`.focal-point-picker__canvas`, `getBoundingClientRect()`, `setPointerCapture()` на `pointerdown` — события не теряются, даже если курсор уходит за пределы канваса до отпускания), координаты — округлённые проценты 0..100. Рядом — превью кропа в трёх пропорциях (`--square` 1:1, `--wide` 16:9, `--tall` 3:4, `object-fit: cover` с тем же `object-position`, что и реальное применение в `NewsCard`). **`pointChange` (живое превью, каждое движение) vs `pointCommit` (один раз на `pointerup`/потерю указателя)** — починка бага «маркер прыгает в центр при отпускании» (вызывающая сторона слала `PATCH` на КАЖДЫЙ `pointChange`, десятки запросов за одно перетаскивание, любой упавший сбрасывал точку): пока идёт драг, маркер рисуется по внутреннему `livePoint` (не по входному `point()`), на `pointCommit` `livePoint` очищается — родитель обязан синхронно отразить закоммиченное (или откатное при ошибке) значение обратно в `point()`, иначе на кадр вернётся прежнее значение. Кнопка «Сбросить в центр» эмитит `null` в оба вывода явно, не `{x:50,y:50}`. Чисто презентационный — ничего не сохраняет и не знает про backend, вызывающая сторона (`PinnedGridEditor`) решает, когда персистить (`AdminNewsService.updateImageFocalPoint()`), подписываясь на `pointCommit`, не на `pointChange`.
- `Button` (`stream.Front#89`) — `src/app/shared/components/button/` — тонкая обёртка над PrimeNG `pButton` для админ-панели (`AdminUsersPage`/`AdminSchedulePage`, `stream.Front#76`/`#77`, ранее использовавших сырую `pButton`-директиву напрямую без единого компонента). Не полный проксирующий враппер PrimeNG API — только пропсы, реально нужные текущим usages: `text` (`input.required<string>()`, содержимое кнопки), `severity` (тип `ButtonSeverity = 'danger'`, единственный нестандартный severity в usages — кнопки «Удалить»), `size` (тип `ButtonSize = 'small'`, единственный нестандартный размер в usages), `disabled`. Остальные PrimeNG severity/`outlined`/`text`-варианты и полная шкала размеров сознательно не заведены — отдельными задачами по мере необходимости (см. AC `#89`). `icon` — опциональный `input<string>()` (класс PrimeIcons, например `'pi pi-trash'`), рендерится как `<i [class]="iconClass">` перед текстом внутри самого `pButton`-хоста через `@if` — если не передан, `<i>` в DOM вообще не появляется (не пустой слот); выбран этот подход, а не content projection (как у `DecorativeButton`), потому что `pButton`-директива в PrimeNG 22 больше не имеет отдельного `icon`-инпута/дочерней `pButtonIcon`-директивы (deprecated с v21) — рекомендованный способ произвольного элемента внутри хоста ближе к простому input-строке для этого тонкого враппера, чем к кастомному SVG-слоту. `severity="danger"` перекрашен в `button.scss` через CSS-переменные, которые генерирует PrimeNG dt()-токенами (`--p-button-danger-background`/`-hover-background`/`-active-background`/`-border-color` и т.д.) — на значения уже существующего в проекте красного (`$color-cf1717`/`$color-c61718`, тот же, что у `ErrorMessage`), а не дефолтного Aura-красного из `AdminPreset` (тот его не переопределяет, см. «PrimeNG» ниже) — так же, как и остальные цвета проекта, не хардкожены инлайн, донастраиваются в одном месте без изменения структуры компонента. **`primeicons` package (`stream.Front#89`)** — до этой задачи не был установлен вовсе, из-за чего `icon()` изначально рендерил класс без реальных иконок (пустой квадрат/ничего): добавлен в зависимости (`npm install primeicons`) и подключён глобально в `angular.json` (`architect.build.options.styles`, `primeicons/primeicons.css` перед `src/styles.scss`) — без этого шага PrimeIcons-классы (`pi pi-*`) не резолвятся ни в одном компоненте проекта, не только в `Button`. **`severity="primary"` (дефолт, доуточнение по прямому запросу пользователя)** — тем же приёмом, что и `danger`, перекрашен в `button.scss` через `--p-button-primary-background`/`-border-color`/`-color` на `$color-f4d2a4`/`$color-f8ecb3`/`$color-76511c` (новые токены в `_variables.scss`, не из designTokens JSON-экспорта) — без этого рисовался бы цвет `AdminPreset`-палитры (`primary: palette('#e6c319')`). Эта же путаница касалась и высоты (40px) — тоже не применялась до перехода на `:host ::ng-deep`, из-за чего инпут визуально был ниже `TextField`/`Select`. **Русская локализация** (по прямому запросу пользователя) — не per-компонентный input (в этой версии PrimeNG для `p-datepicker` его нет), а глобальный `translation` в `providePrimeNG()` (`src/app/core/primeng/ru-translation.ts`, подключён и в `app.config.ts`, и в `.storybook/preview.ts` — та же точка, что и `AdminPreset`-тема): названия месяцев/дней недели, `firstDayOfWeek: 1` (неделя с понедельника), `dateFormat: 'dd.mm.yy'` (двойное `yy` — полный 4-значный год, см. `formatDate()`/`case 'y'` в `primeng-datepicker.mjs`), `today`/`clear`/`choose*`/`prev*`/`next*` и часть общих ключей (`accept`/`reject`/`upload` и т.п., используются и другими PrimeNG-компонентами, не только `Datepicker`) — переведены полностью; остальные (менее употребимые в проекте) ключи не тронуты, английский дефолт. **`inline`** (по прямому запросу пользователя — календарь всегда открыт, без попапа по клику на инпут) — дефолт `false` (не меняет поведение существующих usage), пробрасывается напрямую в одноимённый нативный input `p-datepicker`; в этом режиме у `p-datepicker` вообще нет `<input>` (`@if (!inline())` в `primeng-datepicker.mjs`), значит и наши стили `--p-inputtext-*`/`:host ::ng-deep .p-datepicker-input` просто не к чему применяться — не мешают. `appendTo` в шаблоне (`datepicker.html`) стал условным — `[appendTo]="inline() ? undefined : 'body'"`: `appendOverlay()` у `p-datepicker` не смотрит на `inline()` и буквально переносит панель в конец `<body>` при заданном `appendTo="body"` независимо от режима — при `inline=true` это утащило бы всегда открытый календарь из его законного места в разметке. Фиксированная ширина (`240px`, см. выше) тоже условная — снимается классом `datepicker--inline` (`[class.datepicker--inline]="inline()"` в `host` метаданных `@Component()`, т.к. это класс на **хосте** компонента, а не на элементе внутри его собственного шаблона — обычный `[class.x]` в `datepicker.html` тут не годится) на `:host`, потому что в инлайн-режиме `.p-datepicker`/инпут не рендерятся вовсе — ширину диктует сама панель, особенно с `numberOfMonths` > 1 (см. ниже), где 240px обрубили бы второй месяц. **`numberOfMonths`** — нативный проп `p-datepicker` (несколько месяцев рядом в ОДНОЙ панели при `range`-выборе), пробрасывается как есть, дефолт `1`; показывает только СОСЕДНИЕ месяцы (общая пара `currentMonth`/`currentYear` на весь набор в `p-datepicker` — независимого состояния на панель нет) — для произвольной разницы между месяцами см. `DatepickerRange` ниже. **`defaultDate`** — нативный проп `p-datepicker` (какой месяц показан изначально, пока `value` пуст) — пробрасывается НЕ напрямую, а через `resolvedDefaultDate` (`computed`, "гасится" в `undefined` через `queueMicrotask` в `ngOnInit()` сразу после первого применения); понадобился `DatepickerRange` (см. ниже), чтобы задать разные стартовые месяцы двум независимым инстансам. Причина, по которой напрямую нельзя — реальный баг PrimeNG, всплывший ТОЛЬКО в комбинации с `minDate` (см. подробный разбор ниже, у `DatepickerRange`): `isSelectable()` в `primeng-datepicker.mjs` читает `this.currentView()` только в ветке `minDate` (не `maxDate` — асимметрия в исходнике), что делает внутренний `effect()` для `minDate`/`maxDate` случайно зависимым от переключения date/month/year view; будясь при открытии month-picker, он в ту же волну будит СОСЕДНИЙ `effect()` для `defaultDate`, который безусловно перезаписывает текущий месяц обратно на `defaultDate`, откатывая ЛЮБУЮ навигацию пользователя. **`minDate`/`maxDate`** — нативные пропы `p-datepicker` (даты вне диапазона рендерятся `disabled`, физически некликабельны), пробрасываются как есть — понадобились `DatepickerRange`, чтобы жёстко запретить выбрать в одном календаре дату по не ту сторону от даты в другом (по прямому запросу пользователя). **`rangeHighlight`** (`[Date, Date] | null`, по прямому запросу пользователя — визуально выделить весь выбранный диапазон, не только его края) — реализовано через `dateTemplate` (`<ng-template #date>` в `datepicker.html`, единственный официальный способ PrimeNG добавить что-то на каждую ячейку дня — `::ng-deep` на `.p-datepicker-day` не умеет отличить одну дату от другой, CSS не считает даты) — рисует `<span class="day-range-fill">` позади номера дня, залитый (`$color-e1bf90`, тот же оттенок, что у hover/промежуточных дней `range`-режима выше), если дата строго МЕЖДУ `start`/`end` (сами края красятся штатной `.p-datepicker-day-selected` для `value` конкретного инстанса, см. выше). Контент `<ng-template #date>` физически принадлежит шаблону ЭТОГО компонента (спроецирован через `ngTemplateOutlet` дочерним `p-datepicker`), поэтому несёт наш `_ngcontent`-атрибут и стилизуется ОБЫЧНЫМ (не `::ng-deep`) селектором — в отличие от `.p-datepicker-day`/панели, которые рендерит собственный шаблон `p-datepicker`. **Стекинг заливки — две последовательные ошибки, обе исправлены**: сперва стоял `z-index: -1` — прятал заливку ЗА непрозрачным фоном соседних ячеек в общем стекинг-контексте таблицы дней (видна была только на редких ячейках "чужого" месяца). Убрали `z-index` вовсе (расчёт на то, что порядок в разметке — заливка раньше `{{ date.day }}` — сам расставит слои), но это ОКАЗАЛОСЬ НЕВЕРНО тоже: по CSS 2.1 Appendix E позиционированные потомки без `z-index` (т.е. `auto`) красятся стекинг-контекстом ПОЗЖЕ обычного строчного контента НЕЗАВИСИМО от порядка в DOM — залитые (промежуточные) дни диапазона полностью теряли цифру, видимую только у самих концов диапазона (`.p-datepicker-day-selected`, где заливка прозрачна — `isDateInRange()` намеренно исключает края строгим `>`/`<`). Финальный фикс — число обёрнуто в `<span class="day-number">` с явными `position: relative; z-index: 1` (не сама заливка!) — гарантированно красится после заливки (`z-index: auto` = уровень стека `0`, `1 > 0`) независимо от DOM-порядка. **Month-view/year-view** (`.p-datepicker-month`/`.p-datepicker-year`, открываются кликом по названию месяца/года в шапке — отдельные от дней элементы, свои dt()-токены) — тем же приёмом, что дни (цвет текста/hover/selected), иначе наследуют тёмную `AdminPreset`: текст невидим (светлый на светлой панели), а hover/"выбрано" красились дефолтным жёлтым `AdminPreset` вместо наших цветов (баг всплыл визуально уже после первой версии компонента — переопределили тогда только `.p-datepicker-day`/`.p-datepicker-select-month`/`-year` в шапке, но не сами сетки month-view/year-view). - `DatepickerRange` (`stream.Front#109`) — `src/app/shared/components/datepicker-range/` — композиция из ДВУХ независимых `Datepicker(inline, selectionMode="single")` для произвольной разницы между показанными месяцами (например, слева январь — справа декабрь), которую `numberOfMonths` у `Datepicker` не даёт (см. выше). **Почему НЕ `selectionMode="range"` с общим `value` между двумя инстансами** (первая попытка, не сработала — важный урок, см. подробный комментарий в `datepicker-range.ts`): у `p-datepicker` ЛЮБАЯ внешняя перезапись `value` (в т.ч. тем же значением, которое инстанс только что сам эмитировал через `(ngModelChange)` — а именно так ведёт себя `[ngModel]="value()"` на `Datepicker`, сигнал перегоняет то же значение вниз при каждом ре-рендере) вызывает `writeControlValue()` → `updateUI()`, которая безусловно пересчитывает показанный месяц из `value` (`primeng-datepicker.mjs`). Для незавершённой пары `[date, null]` там баг: код берёт `propValue[1]` (конец диапазона), тот `null` → `isValidDate(null)` ложь → фолбэк на `new Date()` — оба календаря прыгали на "сегодня" уже на первом клике вместо января/декабря; даже без этого бага для ЗАВЕРШЁННОЙ пары `updateUI()` навигировал бы ОБА календаря на месяц `value[1]`, разрушая саму идею "разные фиксированные месяцы". Итоговое решение — `selectionMode="single"` на каждом инстансе (там нет партиал-состояния: клик всегда даёт полную дату из уже показанного месяца, "прыжок" на её же месяц — no-op, ничего не ломается), каждый со своим ЛОКАЛЬНЫМ `[(value)]` (`leftValue`/`rightValue`, `model()` на `DatepickerRange`), никогда не связанным с другим инстансом напрямую. **Левее не может быть правее** (по прямому запросу пользователя) — `[maxDate]` левого календаря = `rightDate()`, `[minDate]` правого = `leftDate()` (нативные `Datepicker`-пропы, см. выше): недопустимые даты — `disabled`, физически некликабельны, не пост-фактум сортировка значения; из-за этого `value` больше не нужно сортировать — порядок `left <= right` гарантирован самим UI. **Заливка выбранного диапазона** (по прямому запросу пользователя) — `[rangeHighlight]="value()"` прокинут в оба календаря (см. `rangeHighlight` у `Datepicker` выше); работает и для дней, до которых долистали вручную в любом из двух календарей — сравнение чисто по датам, не привязано к тому, какой инстанс их показывает. **Единая карточка** (по прямому запросу пользователя — "как единый элемент") — общие рамка/тень/скругление на `:host` этого компонента, у дочерних панелей (`:host ::ng-deep .app-datepicker-panel`, реальный физический предок в DOM — в inline-режиме панель НЕ уносится `appendTo`, см. `Datepicker`) рамка/тень сняты, `border-radius: 0`; вместо расчёта скругления только для "внешних" углов каждой панели по отдельности (как у `ButtonGroup`) — более простой приём: панели становятся прямоугольными, а `overflow: hidden` на этой обёртке сам обрезает их по скруглению внешней рамки; между календарями — `border-right` на первом (не отдельная разделительная `<div>`). `value` — **только для чтения** (`computed()`, не `model()` — задать его снаружи означало бы переписать `value` одного/обоих `p-datepicker`, вернув ровно ту же проблему), пара `[leftDate, rightDate]`. `leftDefaultDate`/`rightDefaultDate` — какой месяц показан в каждом календаре изначально, пробрасываются в `defaultDate` соответствующего `Datepicker`; дальше каждый календарь листается своими стрелками независимо. **Баг PrimeNG: навигация по месяцам ломалась ТОЛЬКО у календаря с `minDate`** (обнаружен уже после выбора полного периода — правый календарь переставал реагировать на выбор другого месяца, откатываясь обратно; левый работал исправно) — см. подробный разбор в `datepicker.ts` у `defaultDate`/`resolvedDefaultDate`: причина в `isSelectable()` (`primeng-datepicker.mjs`), которая читает `this.currentView()` ТОЛЬКО в ветке проверки `minDate` (у `maxDate` аналогичного чтения нет — асимметрия в исходнике PrimeNG); это создаёт СЛУЧАЙНУЮ зависимость внутреннего `effect()` для `minDate`/`maxDate` от переключения date/month/year view, из-за которой открытие month-picker будит и СОСЕДНИЙ `effect()` для `defaultDate` — тот безусловно перезаписывает `currentMonth`/`currentYear` обратно на `defaultDate`. Исправлено на нашей стороне (`Datepicker`, не в `DatepickerRange`) — `defaultDate` нужен только для НАЧАЛЬНОГО месяца, поэтому пробрасывается в `p-datepicker` не напрямую, а через `resolvedDefaultDate` (`computed`, "гасится" в `undefined` через `queueMicrotask` в `ngOnInit()` сразу после первого применения) — эффект PrimeNG проверяет `defaultDate !== undefined` и с этого момента, даже спонтанно перезапустившись, ничего не перезаписывает. Юнит-тесты (`datepicker-range.spec.ts`) покрывают рендер двух `app-datepicker`, разные стартовые месяцы, то, что клик по дате НЕ сдвигает месяц ни в одном из календарей, корректный упорядоченный диапазон при клике в любом порядке, `disabled`-состояние дат по не ту сторону от уже выбранной (`maxDate`/`minDate`), заливку дней строго между выбранными (`rangeHighlight`, в пределах одного видимого месяца) и регрессию на баг с навигацией по месяцам у календаря с `minDate` ПОСЛЕ выбора периода (месяцы в тесте — на английском: `ru-translation.ts` подключена глобально только в `app.config.ts`/`.storybook/preview.ts`, `TestBed` её не использует). Демо — `datepicker-range.stories.ts` (`Shared/DatepickerRange`): "слева январь, справа декабрь" (через `render`/`props`, не `args` — `args` в Storybook сериализуются и теряют `instanceof Date`, из-за чего `defaultDate` тихо падал на "сегодня" в демо, тот же приём, что у `Select.WithValue`/`Datepicker.Open`).

Подложка-«стрелка»/её граница при этом были рассчитаны на растяжение под ширину бокса сегмента по ФИКСИРОВАННОМУ индексу (`segmentBoxes()[0]` для начальной, `[length-1]` для конечной) — при `direction: 'right'` она экранно уезжает под сегмент с ПРОТИВОПОЛОЖНЫМ индексом, но продолжала растягиваться под ширину "своего" (неверного) сегмента. Регрессия закрыта тестами в `list-item.spec.ts` (асимметричные сегменты + `direction: 'right'` — подложки растягиваются под верный бокс, разделитель — на границе текстовых боксов).
  **Роль сегмента определяет тип его подложки — начальная/конечная/центральная**, по прямому запросу пользователя ("если элементов 2 — только начальная и конечная, если 4 — есть начальная, конечная и 2 центральные, если 1 — только центральная"): 1-й сегмент (при `segments().length >= 2`, `hasStartAndEnd()` в `list-item.ts`) — «начальная», последний (при >=2) — «конечная», сегменты МЕЖДУ ними (индексы `1..N-2`) — «центральная», по одной штуке на каждый (`centerSubplates()`, N-2 штук: 0 при N<=2, 1 при N=3, 2 при N=4). При N=1 начальной/конечной нет вовсе (нет `@if (hasStartAndEnd())`-блоков в шаблоне — сама пилюля-силуэт `filter0_d`/`filter3_d` рендерится как обычно, это её собственная форма, не подложка) — только 1 центральная подложка со статичной геометрией (соло-бокс, см. выше).
  Каждая центральная подложка (`paint6_radial`-rect, `<rect>` без 9-slice/`clip-path`, простой прямоугольник) — **ровно `segmentBoxes()` её собственного сегмента**, `centerSubplates() = segmentBoxes().slice(1, -1)` — та же геометрия, что и у текста, никакой отдельной формулы «отступ от разделителя» не нужно (уже заложено в `BOUNDARY_GAP` при построении самих боксов). Каждая — свой инстанс градиента `paint6_radial-{uid}-{index}` (общий на все не подходит: у каждой свои `x`/`width`, `gradientTransform` пересчитывается индивидуально через `centerSubplateGradientTransform()`, формула центр/масштаб).

Тулбарный тоггл «глаз» (`showOnlyViewed`) по-прежнему НИЧЕГО не фильтрует — флаг теперь реальный, но фильтрация архива по нему отдельная будущая задача, не входила в эту. **Тег/дата-фильтр сайдбара применяется ТОЛЬКО к сетке** (клиентская фильтрация уже загруженного списка) — на реальный архив больше не накладывается: полноценная интеграция серверного `GET /news?tagId=`/периода в архив — отдельная будущая задача (текущий контракт не поддерживает диапазон дат).
  **Layout страницы — фиксированная адаптивная высота, пока лента стоит сбоку, без вертикального скролла (`stream.Front#112`; условие уточнено в `#126` — раньше «на `large`»)**: `:host { height: 100%; overflow: hidden }` — тот же паттерн, что `.shell__content`/`.shell` (`shell.scss`, `height: 100vh` цепочкой сверху вниз до `Shell`) — страница явно занимает ровно оставшееся от шапки место; `.news-page` — `flex: 1; min-height: 0`, `.news-page__grid` (`PinnedNewsGrid`) растягивается на всю эту высоту (`align-items: stretch` по умолчанию), `.news-page__archive` — `align-self: flex-start` (сохраняет прежнюю content-based высоту, список внутри и так ограничен собственным `max-height`/скроллом плюс теперь infinite scroll). **Фон страницы — по прямому запросу пользователя НЕ белый фрейма макета**, а унаследован от глобального тёмного `radial-gradient` (`_reset.scss`) — карточки/панель архива остаются светлыми (`$color-f9f9f9`), `.news-page__empty` (архив, единственный текст прямо на фоне) — белый.
  **Адаптив (`stream.Front#122`, правило — ОРИЕНТАЦИЯ, не только ширина — `pinned-grid-rework`)** — `viewport` (`private`, `computed`-подобный `toSignal` над `BreakpointObserver.observe([LARGE_QUERY])`, `@angular/cdk/layout` + `@shared/utils/breakpoints`) резолвит текущий `PinnedGridViewport` (`'large'` при `state.matches`, иначе `'small'` — единственный запрос вместо трёх, `middle`-пресет убран); `effect()` в конструкторе читает `viewport()` и зовёт `PinnedGridService.getLayout(viewport)` — срабатывает один раз при инициализации (реальным значением, `BreakpointObserver` эмитит текущее совпадение синхронно при подписке) и затем повторно ТОЛЬКО когда резолвнутый пресет меняется (Angular signals не перезапускают `effect()` на повторную эмиссию с тем же значением) — лишних запросов на каждый пиксель ресайза/при инициализации нет (см. тесты `news-page.spec.ts`). Каждый пресет — ОТДЕЛЬНАЯ раскладка с бэка (свои `slots`/`columns`/`rows`, не одна сетка, визуально сжимающаяся CSS-ом, см. `PinnedGridEditor`). **Положение ленты — по доступной ширине, а не по пресету (`stream.Front#126`, `АДП-О-12`).** Раньше колонку включал `@include bp.small`: стоило окну пройти в `large`, лента вставала сбоку и забирала `flex: 0 0 660px` независимо от остатка — на 1024×768 витрине доставалось 134 точки. Теперь ширины ленты и зазора — `clamp()`-формулы из `_news-layout.scss` (лента сжимается первой, зазор последним, витрина — остаток), а решение «сбоку или снизу» приходит из `isNewsArchiveBeside()` (`news-layout.ts`) в виде хост-класса `.news-page--archive-below`. Класс переключает СРАЗУ всё состояние страницы, иначе правка неполна: `:host` теряет `height: 100%`/`overflow: hidden` и переходит на document-level скролл (иначе перенесённая вниз лента была бы обрезана), `.news-page` — в колонку, `.news-page__archive` — полноширинный блок, `.news-page__archive-list` — без собственного `max-height`/скролла, `PinnedNewsGrid` получает `.pinned-news-grid--auto-height`. Ширину окна компонент держит числом (`viewportWidth`, `(window:resize)`/`(window:orientationchange)` в `host`), а не медиа-запросом: порог не самостоятельная величина (`РАЗ-Ф-03`) и зависит ещё от паддинга, разного на пресетах — двумя копиями в CSS он бы разошёлся с минимумами. Паддинги `:host` (Figma-макета под мобильную/планшетную версию нет) — `60px` (`large`) / `20px` (`small`, единое значение — раньше было два промежуточных 32/20 под три пресета), подобраны вручную; паддинг — единственное, что решает пресет: он про плотность вёрстки, а не про раздел ширины. **От `1920px`** (`bp.$content-max-width`) — `.news-page` получает `max-width`/`margin: 0 auto` СИНХРОННО с `.shell__header` (`shell.scss`, то же значение `$content-max-width`) — левый край сетки продолжает совпадать с логотипом шапки на любой ширине (см. `Shell` выше). **Тулбар архива** — `ButtonGroup` с `Button icon="pi pi-minus"` (`resetArchiveFilters()`) + двумя `Checkbox` в `buttonMode` (`pi pi-eye`/`pi pi-heart`), и триггер `NewsFilterSidebar` справа — прижат к правому краю явным `margin-left: auto` на `.news-filter-sidebar__trigger` (`stream.Front#121`, `gap` самого тулбара убран как избыточный при этом приёме). Семантика (доработана `#118`): «сердце» фильтрует уже загруженные строки архива по реальному `likedByCurrentUser`; **«глаз» намеренно ничего не фильтрует** (по прямому запросу пользователя) — реальный API пока не отдаёт флаг "просмотрено мной" (view-tracking — отдельная будущая задача), кнопка/сигнал `showOnlyViewed` остаются в интерфейсе, но никуда не подставляются; `minus` сбрасывает оба тоггла. Пустой результат — собственный текст, скрыт во время загрузки (`isLoadingArchive()`), чтобы не мигать между страницами infinite scroll. **Известные отклонения от макета:** на очень маленьких/узких ячейках сетки карточки визуально теснее, чем в макете (адаптивная высота строки — прямое следствие требования "без скролла на любом экране", stream.Front#112).
- `MainCarousel` (`stream.Front#28`) — `src/app/features/main/components/main-carousel/` — специфичный для главной страницы компонент карусели (не абстрагирован под общий переиспользуемый слайдер), `position: fixed; inset: 0` на весь viewport (Full HD и кратные — другие разрешения не проверялись). Ровно 2 слайда (`activeIndex` signal, `next()`/`prev()`/`goTo()` с зацикливанием). Картинка слайда — `imageUrl0`/`imageUrl1` (URL, источник hero-изображений этой задачей не определён — на превью тестовые файлы `public/images/main-carousel/`) + `imagePosition0`/`imagePosition1` (`'left' | 'center' | 'right'`, на всю высоту, `object-fit: contain`). Контент — 3 именованных слота контент-проекции по фактической разметке макета: `[mainCarouselSlide0BottomRight]` (Расписание, `ScheduleWidget` — `#30`), `[mainCarouselSlide0BottomLeft]` (Соц. сети, `SocialLinksBlock` — `#32`), `[mainCarouselSlide1BottomLeft]` (Топ донатеров, `DonatorsWidget` — `#31`) — все три подключены в `main-page.html`. При смене слайда картинка и контент уезжают в сторону своего же позиционирования (`translateX` + `opacity`, без общего fade всего слайда — во избежание визуальной вспышки при наложении). Стрелки навигации — точный SVG из макета (`public/icons/main-carousel-arrow.svg`, правая стрелка зеркалируется через `transform: scaleX(-1)`). Автопрокрутка — 10 секунд на слайд, зациклена (`setInterval` 50мс тик, `progress` signal 0..1); таймлайн внизу — сегмент на слайд, активный заполняется в реальном времени по `progress`, пройденные — полностью залиты; ручная навигация (стрелки/`goTo`) сбрасывает отсчёт. Проверено юнит-тестами (навигация, автопрокрутка/сброс таймера на fake timers, классы позиции картинки, рендер спроецированного контента через host-компонент).

Денормализовано backend'ом в ответ `GET /news/pinned-layout/:viewport` для рендера — РЕАЛЬНО принадлежит картинке (`AdminNewsImage.focalX`/`focalY`, `features/admin/models/news.model.ts`), правится отдельным запросом (`AdminNewsService.updateImageFocalPoint()`), не через сохранение раскладки — влияет на все места, где эта картинка показывается, не только на этот слот.

  - `isSlotPlacementValid(candidate, otherSlots, columns?, rows?): boolean` — тонкая обёртка над `validatePinnedNewsSlots([candidate, ...otherSlots], columns, rows).length === 0`, для live-проверки одного кандидата на каждый `pointermove`/при добавлении в `PinnedGridEditor`.
  - `computeGridResizeImpact(slots, newColumns, newRows): { updatedSlots, clippedNewsIds, removedNewsIds }` (`stream.Front#118`) — считает эффект смены размера сетки: `colStart`/`rowStart` НИКОГДА не трогаются (по прямому запросу пользователя — не смещать карточки), слот, выходящий за новые границы только `colSpan`/`rowSpan`, обрезается (`clippedNewsIds`); слот, чей `colStart`/`rowStart` уже за пределами новой сетки, обрезать невозможно — идёт в `removedNewsIds`. `PinnedGridEditor` показывает результат в `ConfirmModal` перед применением при уменьшении (см. «Компоненты»).

## Interceptors / Guards

- `withCredentialsInterceptor` (`stream.Front#14`) — `src/app/core/interceptors/` — форсит `withCredentials: true` на всех HTTP-запросах приложения (не только через `AuthService`/`ApiService`), чтобы httpOnly auth-cookie уходила глобально; подключён в `app.config.ts` через `provideHttpClient(withInterceptors([...]))`
- `authInterceptor` (`stream.Front#5`) — `src/app/core/interceptors/` — на `401` вызывает `AuthService.logout()` и показывает уведомление через `NotificationService` (без редиректа — окно логина/регистрации реализовано как модалка, без отдельного роута). Исключение — запросы к `/auth/*`: `401` от `/auth/me` (гость, см. `#14`) и `/auth/login`/`/auth/google` (неверные креды) не триггерят logout, а `/auth/logout` явно исключён из собственной же логики, иначе получился бы бесконечный цикл. Ошибка не глотается — пробрасывается дальше вызывающему коду. Backend-эндпоинты и CORS credentials-режим (`streamer.API#16-19`) ещё не реализованы — проверено юнит-тестами на `HttpTestingController`.
- `authGuard` (`stream.Front#20`) — `src/app/core/guards/` — `CanActivateFn`, проверяет только факт авторизации (`AuthService.isAuthenticated()`), без ролей (RBAC — отдельная задача). Неавторизованных редиректит на `/` (не на `/login` — окно логина модалка, без роута). Ложный редирект до завершения `fetchCurrentUser()` при старте исключён архитектурно — `provideAppInitializer` (`#14`) блокирует первую навигацию роутера до готовности `currentUser`, поэтому сам guard не нуждается в асинхронном ожидании. Первое реальное применение — `/account`.
- `adminGuard` (`stream.Front#74`) — `src/app/core/guards/` — `CanActivateFn`, RBAC-проверка роли `ADMIN` (`authService.currentUser()?.role === 'ADMIN'`). Не дублирует проверку факта авторизации — используется на роуте вместе с `authGuard` (`canActivate: [authGuard, adminGuard]`, именно в этом порядке), сам полагается на то, что `currentUser` уже определён к моменту своей работы. Редирект не-ADMIN — на `/`, тот же паттерн, что у `authGuard`.

Пороги совпадают с именами `PinnedGridViewport` (`@features/news/models/pinned-news-slot.model`) — теперь ДВА пресета, не три (`middle` убран): по одной ширине планшет книжкой от планшета альбомом не отличить (iPad Pro 12.9 книжкой — 1024px, шире обычного планшета альбомом), поэтому правило учитывает и ширину, и высоту, и ориентацию:
  ```
  large  = (orientation: landscape) and (min-width: $breakpoint-tablet-min-width /* 768px */) and (min-height: $breakpoint-tablet-min-height /* 600px */)
           or (min-width: $breakpoint-large-min-width /* 1280px */)
  small  = всё остальное
  ```
  `min-height: 600px` в условии `large` — не придирка: телефон в альбомной ориентации (~844×390) по ширине "альбомный и ≥768", но на сетку остаётся ~250px высоты, десктопное бенто там нечитаемо — без этого условия телефон боком получил бы большую раскладку. `$content-max-width` (`1920px`) — порог, после которого широкий контент центрируется, а не растягивается на всю ширину (см. `NewsPage`/`Shell` ниже), не завязан на `large`/`small`. Миксины: `large` (комма-список из двух AND-условий = OR, чистый CSS без `not`), `small` (дополнение — три комма-условия, эквивалентные `(max-width: 1279px) and (orientation: portrait OR max-width: 767px OR max-height: 599px)` по раскрытым скобкам; раньше назывался `middle-down`, объединение `small`+`middle` — с уходом `middle` совпадает с обычным `small`) и `wide` (`min-width: $content-max-width`, независим от `large`/`small`). Подключается как `@use 'breakpoints' as bp;` (`includePaths` в `angular.json`, тот же приём, что `variables`/`mixins`), применяется `@include bp.<имя> { ... }`. **TS-зеркало для `@angular/cdk/layout` `BreakpointObserver`** — `src/app/shared/utils/breakpoints.ts` (`BREAKPOINT_TABLET_MIN_WIDTH_PX`/`BREAKPOINT_TABLET_MIN_HEIGHT_PX`/`BREAKPOINT_LARGE_MIN_WIDTH_PX` + готовая media-query строка `LARGE_QUERY`, комма-OR тех же двух условий, что и SCSS-миксин `large`; `SMALL_QUERY` — дополнение тем же способом, что `bp.small`; `CONTENT_MAX_WIDTH_PX` — зеркало `$content-max-width`, добавлено в `#126`: из него выводится эталонная ширина витрины, см. `news-layout.ts` ниже) — SCSS-переменные недоступны в TS напрямую, оба файла держатся синхронными вручную при правке любого из них; `LARGE_QUERY` используется `NewsPage` (`BreakpointObserver.observe([LARGE_QUERY])`, `state.matches` — `large`/`small`, single-query вместо трёх), `SMALL_QUERY` — `ModalHost` (см. ниже).
- `src/styles/_news-layout.scss` + `src/app/shared/utils/news-layout.ts` (`stream.Front#126`) — **как витрина и лента делят ширину страницы «Новости»** (спека НОВ, блок `РАЗ`). Две половины одного правила, синхронные вручную (`АДП-Ф-04`): SCSS даёт `clamp()`-формулы вёрстке, TS — то же самое холсту редактора и самому компоненту. Отдельно от `_breakpoints.scss` намеренно: величины описывают СОДЕРЖИМОЕ блоков, а не форму окна, и порогами компоновки не являются (`АДП-О-13`). Токены: лента `660`/минимум `440`, зазор `110`/минимум `20`, достаточная ширина витрины `500`, паддинги страницы `60` (`large`)/`20` (`small`). **Выводимые, не заданные числом:** эталонная ширина витрины (`1920 − 2×60 − 660 − 110 = 1030` — «то, что остаётся после ленты») и порог «лента сбоку» (`440 + 20 + 500 = 960` доступной ширины — сумма минимумов, `РАЗ-Ф-03`: отдельное число разошлось бы с ними при первой правке). Функции: `newsPageContentWidth(screenWidthPx, viewport)` (доступная ширина внутри паддингов, перестаёт расти на пороге центрирования), `isNewsArchiveBeside(contentWidthPx)`, `newsArchiveWidth()`/`newsArchiveGap()`/`newsGridWidth()`. Порядок уступок (`РАЗ-Ф-01`) получается сам, без ветвлений: лента — `clamp(440, A−1140, 660)` (отдаёт первой), зазор — `clamp(20, A−940, 110)` (отдаёт последним, `РАЗ-Ф-04`), витрина — остаток (отдаёт после ленты, `РАЗ-О-01`). Сверка с таблицей спеки — в `news-layout.spec.ts`.
- `src/app/shared/utils/pinned-grid-geometry.ts` (`pinned-grid-rework`, правило раздела ширины вынесено в `news-layout.ts` — `stream.Front#126`) — геометрия реальной площади под сетку закреплённых новостей на странице `/news`, РУЧНОЕ TS-зеркало `news-page.scss`/`shell.scss` (высота шапки `Shell` `64`; размеры блоков страницы — в `news-layout.ts`, см. выше) — единственный источник этих чисел для `PinnedGridEditor` (см. «Компоненты» выше), правка любого из значений в SCSS требует и правки здесь. `resolvePinnedGridViewport(screenWidthPx, screenHeightPx)` (принимает ТЕПЕРЬ и высоту — раньше только ширину, недостаточно для правила с ориентацией) — та же логика, что `breakpoints.ts`/`_breakpoints.scss` (landscape = `width >= height`, `large` = landscape ≥768×600 ИЛИ ширина ≥1280 независимо от ориентации). `computePinnedGridAreaSize(screenWidthPx, screenHeightPx): GridAreaSize` — `{ width, height }`; **с `#126` ветвится по `isNewsArchiveBeside()`, а не по пресету**: лента сбоку → витрина получает остаток после ленты и зазора, высота фиксирована; лента внизу → витрина получает всю доступную ширину, `height: null` (страница на document-level скролле). До этого холст считал, что на `large` лента всегда сбоку, и на 1024×768 рисовал витрине 134 точки — ту же неверную геометрию, что показывала посетителю сама страница. `SCREEN_SIZE_PRESETS`/`CUSTOM_SCREEN_SIZE_KEY` — 5 реальных пресетов размера окна браузера (телефон/планшет книжкой/планшет альбомом/ноутбук/десктоп) + ключ произвольного размера, используются и холстом, и iframe-предпросмотром редактора; проверено, что все 5 резолвятся в ожидаемый пресет по новому правилу (телефон/планшет книжкой → `small`, планшет альбомом/ноутбук/десктоп → `large`).

## PrimeNG (`stream.Front#75`)

- `primeng@22`/`@primeuix/themes@3` — подключены в `app.config.ts` через `providePrimeNG()`, **глобально**, но PrimeNG-компоненты в проекте реально используются только внутри админ-панели (`stream.Front#76`/`#77` и далее) — остальной (не-админский) сайт продолжает жить на собственных компонентах (`DecorativeButton`, `SectionTitle` и т.д.), их PrimeNG нигде не заменяет
- `AdminPreset` (`src/app/core/primeng/admin-preset.ts`) — `definePreset(Aura, {...})` поверх дефолтного пресета `Aura`: border-radius/spacing/типографика — дефолтные значения `Aura` (не переопределяются), перекрашена ТОЛЬКО цветовая палитра через `palette()` (`@primeuix/themes`) из реальных цветов проекта — `primary` из `$color-e6c319` (золотой акцент, как у кнопки «Поддержать»/`NavActiveIndicator`), `surface` косвенно — переопределены primitive-шкалы `slate`/`zinc` (на которые semantic.surface ссылается через `light-dark(...)`) из `$color-1e1e1e` (`$color-black`)
- **Форс тёмного варианта** — `providePrimeNG({ theme: { options: { darkModeSelector: '.p-dark' } } })` + класс `p-dark` на `<html>` (`src/index.html`, статично, без переключателя); дефолт PrimeNG (`darkModeSelector: 'system'`) следует `prefers-color-scheme` ОС посетителя, что не подходит фиксированному тёмному визуалу сайта — без форса компоненты в браузере со светлой системной темой рендерились бы светлыми (белый фон таблицы и т.п., проверено вручную, несоответствие всплыло только в реальном браузере, не в юнит-тестах)
- **Лицензия** — PrimeNG 22 перешла на коммерческую модель (`PrimeUI License`, `node_modules/primeng/LICENSE.md`): бесплатна по Community-условиям (revenue/команда ниже порогов), но требует валидный license key, иначе сама библиотека показывает фиксированный баннер «Invalid PrimeUI License» **поверх любой страницы сайта**, не только там, где используются PrimeNG-компоненты — встроенное поведение самого `providePrimeNG()` при инициализации, не то, что можно ограничить только админкой программно. Key передаётся `providePrimeNG({ license: environment.primengLicenseKey })`; `environment.primengLicenseKey` — плейсхолдер (пусто) до того, как пользователь впишет реальный Community-ключ (см. «Опции окружения» ниже)
- Демо-компонент — `p-table` под `AdminPreset`, story `PrimeNG/AdminPreset` в Storybook (`stream.Front#98`, см. «UI-kit / Storybook» ниже) — только проверка темы/интеграции, не реальное использование
